# Шесть практик по лекциям 3 и 4

Начинайте с учебной копии glina-classroom, [запущенной по инструкции](first-steps.md). Эталон glina-starter нужен преподавателю для сравнения. Учебный пример не заменяет собственный продукт КТ-2. Время ниже совпадает с лекциями; установку программ закончите до пары.

## Практика 1 — главный экран, 25 минут

Откройте PRODUCT.md и напишите три предложения о своём сценарии: пользователь хочет ___; видит ___; после действия ___ получает ___. Найдите lib/workshops.ts и components/workshop-card.tsx. Измените содержание одной записи для своего сценария. Предскажите результат; сохраните; найдите изменённую карточку в браузере. Верните учебные данные, если продолжаете общую демонстрацию. Если работаете со своим продуктом, сохраните осмысленное изменение с объяснением.

Покажите связь: title в данных → заголовок карточки; seatsLeft → доступность. При необходимости поручите агенту ограниченное изменение: «Прочитай PRODUCT.md. Покажи план для изменения ___. Назови файлы и проверку. После моего подтверждения реализуй; не добавляй пакеты и не коммить». Сравните diff с планом и сохраните только свою работу. Готовый исходный экран не выдавайте за свой.

## Практика 2 — состояния, 15 минут

В учебном README уже заполнены четыре адреса расписания. Откройте их и допишите для каждой строки «что вижу / что можно сделать». Измените одну фразу в components/state-view.tsx для своего сценария. Проверьте обновление страницы и действие повтора: error → success того же экрана. Пустое расписание и пустые записи имеют разные сообщения.

Отдельная проба: в lib/workshops.ts временно сделайте все три seatsLeft равными 0. Включите галочку: появится «По этому фильтру занятий нет». «Сбросить фильтр» возвращает три карточки без мест. Затем восстановите 3 / 0 / 2. Это успешные данные без подходящих результатов, а не ошибка запроса. Не оставляйте пробные нули в коммите.

Занесите реальные адреса в README. state после знака ? — подготовленный учебный переключатель. Код обработчика писать не требуется.

## Практика 3 — одна ручная правка, 10 минут

В components/schedule-list.tsx нажмите Ctrl+F / Cmd+F и ищите целиком **grid grid-cols-1 gap-4**. Это строка ul с классами `grid grid-cols-1 gap-4 md:grid-cols-2 xl:grid-cols-3`, не панель фильтра выше. Предскажите увеличение промежутков. Без агента замените здесь только gap-4 на gap-6. Сохраните, проверьте 375/768/1440 и все состояния. В текущей теме промежуток меняется с 16 на 24 px; увидьте это в Computed.

В Source Control должен измениться только выбранный участок файла. Сохраните отдельным коммитом `style: increase card spacing manually`. Если есть посторонние изменения — попросите преподавателя помочь разделить их. Альтернатива — понятная правка текста кнопки; её тоже нужно объяснить и проверить.

## Практика 4 — общие токены, 20 минут

Откройте app/globals.css. В учебной копии уже есть служебная связь темы, но исходная палитра нейтральная. Перенесите три решения:

| Имя | Было в заготовке | Решение «Керамики» |
|---|---|---|
| --background | #f8f8f8 | #faf7f2 |
| --primary | #333333 | #8f3d2e |
| --glina-radius-card | 0.25rem | 0.75rem |

Затем в components/workshop-card.tsx замените `rounded-lg` на `rounded-card`, `text-lg` на `text-card-title`, `p-4` на `p-6`. Это подключает карточку к своим правилам. Основные цвета, размеры и радиусы в готовом результате должны ссылаться на тему, а не обходить её.

Для проверки временно задайте primary #234f74: логотип и активная ссылка в шапке изменятся одновременно. На адресе error изменится и кнопка. Верните #8f3d2e. Проверьте цвет текста на фоне, два элемента с одним токеном, все состояния. Сохраните изменения темы и её потребителей коммитом `style: apply product tokens`. Образец DESIGN.example.md не редактируйте; полную таблицу заполним в своём документе на следующем шаге.

## Практика 5 — DESIGN.md до второго экрана, 12 минут

Создайте в корне **новый DESIGN.md**, пользуясь DESIGN.example.md как образцом. В своём файле заполните таблицу: источник, значения и где они видны; типографика и оставшиеся роли тоже нужны для КТ-2. Образец остаётся неизменным. Переносите только принятые решения: не называйте непроверенные готовыми. Укажите минимум три запрета и заполните DECISIONS.md своим решением и причиной.

Сохраните DESIGN.md отдельным коммитом `docs: define design rules before second screen`. В этот момент app/bookings/page.tsx ещё не существует. Попросите агента прочитать DESIGN.md с диска и назвать, какие правила ограничивают следующий экран. Простое наличие файла не доказывает, что агент прочитал его.

## Практика 6 — второй экран с агентом, 20 минут

Передайте своему доступному агенту следующий текст. Для чтения и ручных упражнений платная подписка не нужна; при отсутствии агента генерацию демонстрирует преподаватель, индивидуальное выполнение фиксируется отдельно.

```text
Прочитай PRODUCT.md, DESIGN.md и существующие components.
После моего подтверждения плана создай /bookings — «Мои записи».
Моковые данные в lib/bookings.ts: кружка — «Запись подтверждена»,
тарелка — «Ожидает подтверждения» (точные тексты для учебных тестов).
Используй существующие WorkshopCard, PageShell, StateView и токены.
У WorkshopCard уже есть statusLabel: в записях вместо свободных мест
покажи текст статуса. Не копируй карточку.
Четыре state как у /schedule; повтор остаётся на /bookings,
из empty ссылка «К расписанию» ведёт к /schedule.
Добавь ссылку «Мои записи» в SiteHeader.
Сначала назови файлы, переиспользуемые части и проверки.
Не добавляй пакеты, вход, оплату или реальный API. Не коммить сам.
```

После реализации проверьте четыре адреса, адаптив и общие стили. Исправления стиля формулируйте через правила/токены и задачу агенту. Не подгоняйте второй экран вручную. Сохраните экран отдельным коммитом и добавьте строки README. В истории коммит правил должен стоять раньше коммита экрана. Копирование готового эталона преподавателя не является выполнением задания с агентом.

## Проверка соседом — 12 минут

Передайте управление **своим** запущенным браузером и README. Сосед открывает error второго экрана напрямую, обновляет, нажимает «Повторить» без мыши. Проверяет empty → расписание, узкий экран, длинное название, два общих значения и историю коммитов. Записывает «адрес / ожидание / факт», включая успешные проверки. Локальный адрес не открывает ваш проект на чужом компьютере.

## После пары

Полная матрица КТ-2: 12 кадров расписания (4 состояния × 3 ширины), 6 записей (4 на 375 + success на 768/1440). Эталон содержит автоматическую проверку, но студент сохраняет собственные актуальные скриншоты. После сборки второго экрана: npm run build, npm run test:final (нужна установка Chromium по README). Это проверяет учебный пример; при смене продукта адаптируйте ожидаемые тексты тестов вместе с преподавателем. Не удаляйте проверки ради зелёного результата.

К сдаче: свой PRODUCT.md, таблица адресов README, DESIGN.md с источником, DECISIONS.md, скриншоты, отдельная ручная правка, история правил до экрана. Готовый starter не подтверждает эти личные результаты автоматически.
